Methodology

How every number on this site was produced: the four-stage pipeline each buggy version runs through exactly once, the suspiciousness formula shared by both rankings, and the line-tolerance and answerability methodology that separates a genuine ranking miss from a fault no technique could ever have found.

How The Data Is Produced

The Four-Stage Pipeline

Each buggy version is checked out once and run through this pipeline exactly once. Every RQ on this site is derived from these four stages' own output — nothing is measured twice with different code.

01

Test Execution & Target Pool

feeds RQ1, RQ3

The full relevant test suite runs once, uninstrumented, as the ground truth for which tests fail and as the baseline timing cost. Every relevant test is then re-run individually to get a clean per-test pass/fail spectrum and, for tests that fail in isolation, that test's own stack trace.

  • Target Pool construction — for every test that fails in isolation, its assertions are walked top-to-bottom up to the exact line its own stack trace names as the failure site. Every assertion reached before that line is labelled Correct (it held); the assertion at the failure line is Incorrect. Anything after it never executed and is ignored.
  • Uncaught_Exception tracking — a failing test whose failure site is not an assertion call at all (it crashed before reaching one) is counted separately, rather than forced into the assertion walk.
02

Dynamic Slicing

feeds RQ2, RQ3

Every Target Pool row seeds one targeted dynamic backward slice, run from the exact variable, line and test that produced it. Slicing every passing test as well would be prohibitively expensive, so passing tests are handled selectively instead.

  • Failing-test criteria — each Target Pool row is sliced directly: a Correct row becomes a Virtual_Pass column, an Incorrect row becomes a Virtual_Fail column.
  • Passing-test criteria (selective) — every passing test's own assertions are scanned statically, and only the ones whose output variable already appears somewhere in the Target Pool are sliced. These always become Virtual_Pass columns.
  • Each resulting slice becomes one virtual test column. Anything the slice reaches outside the project's own source classes — dependency-chain noise from inside the test method itself — is discarded before it can become a matrix row.
03

Matrix Construction & Ochiai Scoring

feeds RQ4

Two independent observation matrices are built from the same buggy version, then scored with one shared Ochiai formula — see Trace vs. Slice below for what each matrix actually contains.

  • Trace matrix — one row per real test case, via per-test coverage instrumentation across the whole project's source, not just the file the bug happens to touch.
  • Slice matrix — one row per virtual test column from Stage 2; columns are the union of every statement any virtual column's slice touched.
  • Both matrices are scored with the identical Ochiai formula, so any difference between the two rankings comes from what each matrix contains, never from two different scoring implementations.
04

Suspiciousness Ranking

feeds RQ5

Statements are ranked by Ochiai score, independently for the trace matrix and the slice matrix, producing two rankings per buggy version that RQ4 and RQ5 then evaluate against the ground-truth fault line(s).

  • Ranking uses standard competition ranking (1-2-2-4): statements tied on Ochiai score all receive the same rank, the top position of that tied group.
  • Every ranked row also carries a tie_size, so the group's worst position, r_worst = rank + tie_size − 1, is always derivable without re-scanning the ranking.

Stage 3, In Detail

Trace vs. Slice: Two Approaches Compared

Every buggy version is scored twice, by two matrices built from the same test run — the difference between them is exactly what this project measures.

Baseline

Trace — Traditional SBFL

  • Rows: every real test case in the suite.
  • Columns: every statement in the project's own source classes, from per-test coverage instrumentation.
  • Coverage is measured per whole test, independent of which assertion it makes or whether that assertion is even related to the fault.
  • This is what a conventional spectrum-based fault localization tool computes on its own.

Proposed

Slice — Hybrid, Slicing-Based

  • Rows: virtual test columns — one per sliced assertion, from both failing-test and selective passing-test criteria.
  • Columns: the union of statements that actually appear in one of those dynamic backward slices.
  • A statement only appears at all if some assertion's dependency chain actually reaches it.
  • This is the reduced search space RQ2 measures, and what RQ4/RQ5 evaluate as the hybrid approach.

Stage 3, In Detail

The Ochiai Suspiciousness Formula

One formula, applied identically to both matrices — an "observation" is a real test case for the trace matrix, or a virtual test column for the slice matrix.

ochiai(s)  =  ef  /  √​( (ef + nf) · (ef + ep) )
e_f — failing observations that covered statement s n_f — failing observations that did not cover s e_p — passing observations that covered s

ⓘ Scores fall in [0, 1]; a statement covered by every failing observation and no passing observation scores 1.0. When the denominator is 0 (no failing observation covers the statement at all), the score is defined as 0. Ties are broken only by the competition-ranking rule in Stage 4, never by a secondary metric.

Stage 5, Evaluation

Line Tolerance & Answerability

The guiding question is not a raw hit rate across every ground-truth fault line — it is the ranking's success rate specifically on the fault detections it could theoretically succeed at, and a systematic account of why it misses the rest.

A ranking's result for one ground-truth fault line is evaluated two ways. First, an exact match: does the true fault line itself carry a rank in this ranking at all? Second, a tolerant match: if not exact, is the ranking's nearest same-file candidate within a small number of lines of the true fault line? Both are always computed and stored — the DIFF control on the RQ5 page only changes which of them counts as a "hit" for a given view; DIFF=0 (exact line only) is the strict, primary result, and DIFF>0 is a deliberate relaxation for understanding near-misses, not a claim that an off-by-N-lines hit is functionally equivalent to an exact one.

Why A Miss Happens

Every non-hit is classified into exactly one of three reasons, read directly from the pipeline's own recorded fields — never re-derived or newly invented after the fact.

SUCCESS

An exact match, or a same-file candidate within the selected tolerance.

PIPELINE GAP

The fault line was structurally reachable, but this specific ranking never produced a same-file candidate to measure against — most often the slice ranking simply never touched that file.

PROJECT-CAUSED

The fault line itself is flagged unanswerable — see below. No technique could find it with this run's own data, regardless of ranking quality.

OTHER MISS

A same-file candidate does exist, but falls outside the currently selected tolerance — would count as SUCCESS at a wider DIFF, not visible at a stricter one.

Answerability

Before any ranking is judged, each ground-truth fault line is checked for whether this run's own checkout and test suite could ever have found it at all. A line flagged unanswerable is excluded from both the numerator and denominator of any success-rate statistic — scoring it as a miss would unfairly penalize the technique for something no technique could ever do with this run's own data.

dead_code_never_executed
The fix is a pure deletion — the "buggy" line does not exist in the buggy build's checked-out source at all, so no execution could ever reach it.
live_line_never_executed
The line exists and could run, but no test in this run's own suite ever exercised it — a genuine gap in the project's test suite, not a limitation of either ranking technique.

Where The Numbers Come From

Data Provenance

loading…

The dataset behind this site was collected by running the identical pipeline code, unmodified, across multiple parallel compute environments and consolidating the results afterward. Every buggy version's status is exactly one of two values: completed (the pipeline ran to completion and produced a full set of rankings) or not available (a target that could not finish — most often a Defects4J checkout or build failure). There is no silent partial-success state: a status is never inferred, backfilled, or estimated.

Every figure, table and chart on this site is generated by resQ_scripts/build_site_data.py reading directly from the pipeline's own output files. Nothing here is hand-entered.

Honesty Notes

Known Limitations

ⓘ Commented-out test methods. A handful of targets across the dataset contain test classes with commented-out test methods (a common convention in some Defects4J-era codebases for manual/network-dependent tests). The pipeline's static test-method scan can occasionally pick one of these up as if it were real, inflating that specific target's failing-test count. This is a known, tracked issue in test-suite bookkeeping — it does not affect which statement is scored as faulty or how either ranking is computed.
ⓘ Line tolerance is a proximity measure, not equivalence. A hit recorded at DIFF>0 means the ranking's best same-file candidate landed close to the true fault line, not on it. Any statistic that reports a DIFF>0 rate alongside a DIFF=0 rate should be read as two different, clearly labelled questions, never averaged together into one number.

Reference

Glossary

Target Pool
The set of (test, variable, line, Correct/Incorrect) rows harvested from every failing test's own isolated run — the raw slicing criteria for Stage 2.
Virtual Test Column
One dynamic backward slice's worth of statements, treated as one observation in the slice matrix. Not a real JUnit test — a derived slicing criterion.
Statement
One non-bracket source line inside the project's own source classes — the unit both matrices' rows are scored over. Test code is never a statement.
Ochiai Score
The [0, 1] suspiciousness score from Stage 3's shared formula — how strongly a statement's coverage correlates with failure.
rank / tie_size / r_worst
Competition ranking (1-2-2-4): tied statements share the same rank; tie_size records the width of that tie; r_worst = rank + tie_size − 1.
DIFF (Line Tolerance)
How many lines away from the true fault line a same-file candidate may fall and still count as a hit. 0 means exact line only.
Answerable / Unanswerable
Whether a fault line could, in principle, ever be found with this run's own checkout and test suite — independent of either ranking technique's quality.
diff_reason
The pipeline's own recorded explanation for a miss — succeed, project_test_scenario or pipeline_gap — that the SUCCESS / PROJECT-CAUSED / PIPELINE GAP / OTHER MISS classification above is read from directly.
